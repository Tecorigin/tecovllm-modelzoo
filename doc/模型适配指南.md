# 算子性能优化比赛指南

> **注意**：提交代码前务必阅读文末 [第 5-6 节 提交说明](#6-提交代码)，确保 run.sh 满足所有要求。

本文档面向参赛开发者，介绍如何在太初 AI 加速卡（SDAA 平台）上对 **OneGenomeRice** 模型进行算子性能优化。整体流程如下：

| # | 阶段 | 说明 |
|---|------|------|
| 1 | 检查推理环境 | 确认开发环境（硬件 + 容器）满足任务需求 |
| 2 | 模型适配 | 模型分析 → 算子优化 → 运行验证 |
| 3 | 精度验证 | 验证推理精度是否达标 |
| 4 | 性能评测 | 测试吞吐、延迟等关键指标 |
| 5 | 添加 README | 为优化后的模型编写使用说明 |
| 6 | 提交代码与 PR | 完成所有测试后提交代码和 PR |

---

## 1. 检查推理环境

开始适配前，建议先熟悉开发环境的软硬件配置，确保容器、框架、加速卡等资源就绪，以便适配和推理过程顺利进行。

### 1.1 检查硬件信息

使用 `teco-smi` 命令查看太初加速卡的设备列表与工作状态：

```bash
teco-smi
```

输出示例：

```
+-----------------------------------------------------------------------------+
|  TECO-SMI: 1.15.0        SDAADriver: 3.1.0        SDAARuntime: 3.1.0        |
|-------------------------------+----------------------+----------------------|
| Index  Name                   | Bus-Id               | Health      SPE-Util |
|        Temp          Pwr Usage|          Memory-Usage|                      |
|=============================================================================|
|   0    TECO_AICARD_01         | 00000002:05:00.0     | OK                0% |
|        42C                98W |        0MB / 65536MB |                      |
|-------------------------------+----------------------+----------------------|
```

重点关注以下字段：

| 字段 | 说明 | 正常状态 | 异常处理 |
|------|------|----------|----------|
| **Memory-Usage** | 设备内存使用状态（已用 / 总量） | 已用内存远小于总量 | 内存占用异常时检查残留进程 |
| **Health** | 设备健康状态 | `OK` | 出现 `DEVICE_LOST`、`HEARTBEAT_ERROR` 等异常时，请联系太初技术支持 |
| **SPE-Util** | SPE 计算核心使用率 | 正常数值 | 显示 `N/A` 表示芯片掉卡，请联系太初技术支持 |

### 1.2 检查容器软件信息

若终端成功输出 Torch-SDAA 及各依赖组件的版本信息，表明运行环境就绪。示例如下：

## 2. 模型适配

### 2.1 模型分析

适配前请完成以下分析，以保障后续流程顺利开展：

1. **模型可运行验证**：确认模型在 CPU 或 GPU 环境下能正常加载并完成基础推理，无报错或异常退出。
2. **量化格式确认**：当前仅支持 **FP16** 和 **INT8** 两种量化格式，其他格式暂不兼容。
3. **并行策略确认**：
   - **TP（张量并行）**：按硬件核组数配置，单卡为 4 核组，单卡运行时 TP = 4。
   - **PP / DP / EP**：并行规则与标准 CUDA 保持一致。
4. **算子选择**：以下算子已在 [算子开发仓库](https://github.com/Tecorigin/teco-ops) 中提供基础版本，参赛者可在此基础上进行性能优化：

| 算子 | 说明 |
|------|------|
| `reshape_and_cache_flash` | KV cache 写入与 reshape 融合算子 |
| `flash_attn_varlen_func` | 变长 Flash Attention 前向算子 |

### 2.2 算子优化

参赛者可基于上述基础版本进行性能优化（如算子融合、优化特定 shape 下的算子性能等）。

**优化指导建议**：

1. 充分理解算法逻辑，设计实现方案时可以结合数学公式看是否可从计算上进行优化
2. 分析算法细节，合理设计任务的粒度和负载均衡，充分发挥众核架构多核心的优势进行并行操作（任务拆解到多个核心并行处理）
3. 充分利用 SPM 优势将数据尽可能多的重复利用，减少主存数据搬运
4. 根据情况可考虑是否需要额外的主存来存储中间计算结果，或者对部分数据进行重计算
5. 一些常用的优化手段包括：双缓冲，向量化计算，负载均衡，主存数据连续搬运等

更详细的性能优化指导，可查阅 [性能优化手册-算子篇](http://docs.tecorigin.com/release/op_perf_opt/v1.1.0/#5728df579b864ac3a8b108b812e60611)。

> ⚠️ **注意**：优化过程中请**仅修改算子内部实现**，保持对外 API 接口不变。接口变更将导致模型组网层和注册层需要额外适配，增加不必要的工作量。

### 2.2.1 自定义算子库编译安装

自定义算子库编译：

1. 下载代码库：`git clone https://github.com/Tecorigin/teco-ops-xxx.git`（xxx代表队名，各参赛队下载带自己队名的仓库代码）

2. 在项目目录下构建自定义算子库 `wheel` 包：

   ```bash
   # 导入Tecorigin软件栈环境变量
   source /opt/tecoai/setvars.sh
   # 构建teco-ops wheel包，仅构建PyTorch 扩展（不包含 Plugin）
   WITH_TORCH=ON WITH_INFERENCE_PLUGIN=OFF python setup.py bdist_wheel
   ```

3. 安装 tecoops 自定义算子库：

   - 构建完成后在项目 `dist` 目录下生成 `tecoops-0.0.0-cp312-cp312-linux_loongarch64.whl` 包
   - 执行 `pip install tecoops-0.0.0-cp312-cp312-linux_loongarch64.whl` 安装。

4. 卸载 tecoops 自定义算子库：`pip uninstall tecoops -y`

5. 更新 tecoops 自定义算子库，提供两种方式：

   - 方式一：先卸载旧的 `tecoops`，再安装新的。
   - 方式二：执行 `pip install tecoops-0.0.0-cp312-cp312-linux_loongarch64.whl --force-reinstall` 强制更新。

### 2.2.2 自定义算子库验证

#### C++ 接口验证

设置 `torch` 的 `lib` 目录到系统环境变量：

```bash
# 获取 torch lib 目录
python -c "import os;import torch;print(os.path.join(os.path.dirname(torch.__file__), 'lib'))" 2> /dev/null | tail -n 1
# 设置系统环境变量
export LD_LIBRARY_PATH=$(python -c "import os;import torch;print(os.path.join(os.path.dirname(torch.__file__), 'lib'))" 2> /dev/null | tail -n 1):$LD_LIBRARY_PATH
```

进入项目的 `test` 目录：

```bash
# 构建所有算子 C++ 接口测试代码
source env.sh
bash build.sh --arch teco

# 执行测试命令
./build/demo --gid=0
```

#### PyTorch 接口验证

进入项目的 `python_api_test` 目录下执行：`pytest -vs .`，测例全部 `pass` 即可。

算子开发及 PyTorch 框架接入方法，请参考 [算子开发仓库](https://github.com/Tecorigin/teco-ops) 中的相关文档。

## 3. 精度验证

模型适配完成后，需通过精度验证确认推理结果正确性。具体流程如下：

### 3.1 精度测试

**环境要求**：vLLM 版本为 **0.20.2**，Evalscope 版本为 **1.8.1**。

> **采样参数**：各模型的采样参数（temperature、top_p、top_k 等）均使用模型官方推荐的设置方式。

#### zhejianglab/OneGenomeRice

**评测数据集**：使用 RiceBenchmark 数据集 Epigenetic_Marks_Prediction-Histone 子集的 test 部分作为测试数据。
**评测方法**：测试模型根据之前的碱基对生成最后一百个碱基的正确性，评价指标使用准确率（accuracy）。
**测试数据**：评测时 `epi_eval.py` 会自动从 ModelScope 下载，无需手动准备。

https://www.modelscope.cn/datasets/ZhejiangLab/RiceBenchmark/resolve/master/Epigenetic_Marks_Prediction-Histone/test.jsonl

**启动 vLLM 服务**（TP=4）：

```bash
vllm serve /tecogpfs/models/zhejianglab/OneGenomeRice \
    --trust-remote-code \
    --tensor-parallel-size 4 \
    --port <port> \
    --host <ip>
```

**运行 epi_eval.py 评测**：

```bash
python tools/ci_pipline/epi_eval.py \
    --host <ip> \
    --port <port> \
    --workers 128 \
```

### 3.2 精度评测基准

各模型评测 10 次取平均分，波动不得超过基线 ±0.05。具体要求见下表。

| 模型 | 数据集 | 子集 | Case 数 | 评分指标 | 基准得分 |
|------|--------|------|---------|----------|----------|
| OneGenomeRice | RiceBenchmark | Epigenetic_Marks_Prediction-Histone | 10000 | accuracy | 0.6902 |

## 4. 性能评测

### 4.1 性能测试

SDAA 平台所有模型的性能评测统一使用 **Evalscope** 框架。通过 Evalscope 指定模型服务 API 端点和数据集进行推理性能压测，得到吞吐量（tokens/s）和请求延迟（TTFT、TPOT）等关键指标。

以下为 OneGenomeRice 的文本性能测试用例（T1 ∼ T3）：

#### T1 — bs=1，32K 输入 / 200 输出

```bash
evalscope perf \
    --model "$MODEL_NAME" \
    --url "$API_URL" \
    --api openai \
    --tokenizer-path "$MODEL_PATH" \
    --dataset random \
    --min-prompt-length 32768 --max-prompt-length 32768 \
    --max-tokens 200 --min-tokens 200 \
    --extra-args '{"ignore_eos": true}' \
    --parallel 1 --number 10
```

#### T2 — bs=1，100K 输入 / 200 输出

```bash
evalscope perf \
    --model "$MODEL_NAME" \
    --url "$API_URL" \
    --api openai \
    --tokenizer-path "$MODEL_PATH" \
    --dataset random \
    --min-prompt-length 102400 --max-prompt-length 102400 \
    --max-tokens 200 --min-tokens 200 \
    --extra-args '{"ignore_eos": true}' \
    --parallel 1 --number 10
```

#### T3 — bs=32，1K 输入 / 1K 输出

```bash
evalscope perf \
    --model "$MODEL_NAME" \
    --url "$API_URL" \
    --api openai \
    --tokenizer-path "$MODEL_PATH" \
    --dataset random \
    --min-prompt-length 1024 --max-prompt-length 1024 \
    --max-tokens 1024 --min-tokens 1024 \
    --extra-args '{"ignore_eos": true}' \
    --parallel 32 --number 320
```

### 4.2 性能指标

| 指标 | 含义 | 说明 |
|------|------|------|
| `TTFT`（ms） | 首 token 延迟 | 请求到达 → 生成首个 token 的耗时 |
| `TPOT`（ms） | 每 token 延迟 | 生成阶段每个 token 的间隔时间 |

### 4.3 性能测试用例汇总

| 用例 | bs | 输入长度 | 输出长度 | Number |
|------|-----|----------|----------|--------|
| T1 | 1 | 32K | 200 | 10 |
| T2 | 1 | 100K | 200 | 10 |
| T3 | 32 | 1K | 1K | 320 |

## 6. 提交代码

模型适配完成并跑通全部测试用例后，即可将新增的模型文件及 README 推送到远程仓库，并提交 PR。

### 6.1 PR 要求

PR 须包含以下三个部分：

1. **模型适配代码**：模型组网文件、注册代码等，按仓库现有结构放置。
2. **`model-adaptations/<团队名称>/README.md`**：适配模型的推理使用说明，格式参考 [第 5 节](#5-添加-readme)。
3. **`model-adaptations/<团队名称>/run.sh`**：可直接运行的 vLLM 服务启动命令，包含完整的模型路径、端口及所有必要参数。

PR 提交流程请参考 [PR 提交规范](./pr提交规范.md)。

### 6.2 评测说明

**你的 run.sh 脚本必须放在对应模型的路径下**，CI 会根据仓库目录自动扫描并调度执行。CI 将依据你的 run.sh 中定义的配置自动执行精度和性能测试，通过标准见 [3.2 精度评测基准](#32-精度评测基准) 和 [4.2 性能指标](#42-性能指标)。

### 6.3 CI 要求

> **⚠️ 以上要求为强制项，不满足将直接导致 CI 报错挂掉，PR 无法合入。**

- **`tools/ci_pipline/` 下的文件不可修改**，否则 PR 无法通过检查、无法合并。
- **`model-adaptations/<团队名称>/run.sh`** 中的命令**必须包含 `--served-model-name`**，且参数必须为 `"OneGenomeRice"`（对应本文档中的模型），否则 CI 会挂。
- **vllm serve 请勿使用默认端口**，通过 `--port` 显式指定端口号，避免与其他任务端口冲突。
- **run.sh 中必须包含 `--trust-remote-code`**，否则部分模型的 tokenizer 或模型配置可能无法正常加载。
- **run.sh 中必须包含 `--no-enable-prefix-caching`**，避免前缀缓存导致性能测试结果不可信。
